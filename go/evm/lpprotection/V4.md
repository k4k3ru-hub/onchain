# V4 LP analysis: discovery and ordinary-owner withdrawal

2026-09-24. Implementation unit 1 of the approved V4 LP-protection plan.

## Scope

Base mainnet, hookless pools, official PositionManager positions only.
Ordinary EOA positions can be classified as `withdrawable`. LaunchLocker,
other contracts, delegated accounts and burn addresses remain unresolved.
Permanent protection and its creation/authority proof are the next unit.
No RPC transport, production dependency, signing or transaction submission is
added. Existing reader constructors and V3 / Slipstream behavior are preserved.

`deployment.ByChainID(8453)` now includes `PositionManager`. Other supported
chains remain available for discovery with a zero PositionManager in this field.

Request additions:

- `Principal.PoolID`: full 32-byte ID for V4, paired with `Principal.Pool`
  containing the PoolManager. Never truncate a Pool ID to an address.
- `ModifyLiquidityLogs`: received pool events, sharing the input log limit
  with `MintLogs`. Existing V3 / Slipstream callers continue using `MintLogs`.
- `Result.PoolID`: preserved alongside the manager/address fields.

The reader uses the existing `clliquidity.V4` complete snapshot. Snapshot
provenance and full tick coverage remain the caller's responsibility; mutable
slot0 and active liquidity are independently matched at the observation hash.

## Validation and discovery

1. Verify Base, official deployments, Initialize ABI, native currency ordering,
   PoolKey hash, spacing and hookless fixed fee. Native token0 zero is valid.
2. Match the creation receipt and its canonical block. Match the complete
   deployed PositionManager runtime, including all immutable values and metadata.
   Check both manager and StateView PoolManager bindings.
3. Reuse acquired/saved receipts and received ModifyLiquidity events first.
   Only official-PM sender salts are token ID candidates. Match the source
   receipt and canonical block before retaining the immutable tick range.
4. Verify each NFT PoolKey, packed Pool ID prefix/ticks, liquidity and core
   position `(Pool ID, manager, lower, upper, salt=token ID)` at one block hash.
   Same-tick NFTs remain separate during this check. Deduplicate IDs.
5. Require exact full-tick gross/net coverage, including out-of-range liquidity
   and sub-unit principal. If candidates are insufficient, request bounded
   ModifyLiquidity history scoped by PoolManager and the full indexed Pool ID.
   Stop once current candidates cover all ticks.
6. A previously discovered position can be omitted after an explicit core zero
   at its canonical recorded range and salt. A missing/reverted NFT getter
   without that binding never means zero. Saved receipts retain ranges after
   NFT burn clears PositionInfo; they are revalidated when reused.

Saved receipts use the existing opaque `Evidence.Acquired` format. This unit
does not change the evidence schema/model version or migrate operator histories.
The next permanent-custody unit introduces the new evidence model and explicit
migration preserving abandoned acquisition ranges.

## Read-only withdrawal

The actual current owner must have empty code and satisfy the existing
ordinary-address restrictions. From that owner, call the official PM with:

- `modifyLiquidities(bytes,uint256)`; deadline = observation time + 1 hour.
- `DECREASE_LIQUIDITY`: the NFT's entire positive liquidity, both minima zero,
  empty hook data.
- `TAKE_PAIR`: both PoolKey currencies, recipient = the same owner.

The fixed ABI payload is 676 bytes. There is no state override, signature,
broadcast or gas expenditure. Success verifies this complete path at that
observation; it does not guarantee private-key availability or future behavior.
Reverts/errors never establish a lock. The reader returns no percentage and
preserves the wrapped error. Unsupported custody also returns no percentage.

For an entirely withdrawable pool, each positive-principal token has locked and
permanent percentages `"0"`, and `AllPositionsProtected=false`. Zero-principal
tokens have nil percentages. A pool with any unresolved positive position has
no pool-wide observation. Token trust, taxes and minting are separate concerns.

## Verification

Tests inject a synthetic, pinned RPC dataset and the recorded PM runtime. The
withdrawal expectation uses go-ethereum's independent ABI encoder. Coverage
includes receipt reuse/restoration, pool-ID isolation, multiple salts, out-of-range
dust, unsupported managers/custody, NFT burn, getter/withdrawal revert, malformed
metadata, reorg and acquisition budgets. Existing V3 / Slipstream tests remain.

The one-NFT synthetic fixture records 17 reader RPC calls cold (one receipt)
and 16 after evidence restoration (zero receipts); both request zero log-history
calls. These are **fake-RPC call counts**, not live latency, provider usage or
OnchainRegistry cache measurements. Complete principal acquisition is external
to this reader and is not counted here.

Run from `onchain/go`:

```sh
GOWORK=off go test ./evm/lpprotection ./venues/uniswap/v4/deployment
GOWORK=off go test -v ./evm/lpprotection -run '^TestV4'
GOWORK=off go vet ./evm/lpprotection ./evm/clliquidity ./venues/uniswap/v4/...
GOWORK=off go test ./...
```

All commands above passed on 2026-09-24, as did `gofmt` verification and
`git diff --check`. The SDK-wide test run also compiles the affected packages.
No service build or live RPC/Agent E2E was performed in this unit.
